## Requirements

| Item | Requirement |
|---|---|
| Host | Any 64-bit Linux host (amd64 or arm64): a mini-PC, NAS, VM or small cloud instance |
| Software | Docker Engine **25.0 or newer** with the Compose v2 plugin **2.20.2 or newer** (the healthchecks use `start_interval`; Compose refuses an older engine with a clear error) |
| Resources | About 1 GB of free RAM and 2 GB of disk for Atlas + Postgres + the bundled IdP. Immich has its own requirements |
| Domain names | **Two HTTPS hostnames you control**: one for Atlas (e.g. `atlas.example.com`) and one for the identity provider (e.g. `id.example.com`). Immich, if you use it, has its own. See [why two](#why-two-hostnames) |
| TLS | Valid, publicly trusted certificates for those hostnames, provided by whatever sits in front of Atlas (a tunnel or your reverse proxy). Self-signed certificates break passkeys and the Immich mobile app |
| Email | **Not required.** Admins hand out reset/enrolment links in person |

### Why two hostnames

The bundled IdP (Kanidm) is the OIDC issuer for Atlas and Immich. It needs its **own origin**, because it can't run under a sub-path of Atlas.

Pick the IdP hostname once and keep it. **Passkeys are bound to that hostname**, so changing it later forces everyone to re-enrol their passkeys. Password + TOTP survive the change. Details are in [ADR-001](adr/001-identity.md#the-bundled-idps-hostname-and-tls-requirements).

## Quick start

```bash
git clone https://github.com/solahuddeen02/atlas.git
```

```bash
cd atlas/deploy
```

```bash
cp .env.example .env
```

Edit `.env` and set at least `ATLAS_PUBLIC_URL` and `ATLAS_IDP_PUBLIC_URL` to your two HTTPS URLs. Everything else has generic defaults. Then install:

```bash
./install.sh
```

`deploy/install.sh` does two things. It creates the external volumes if they're missing: `docker volume create atlas_pgdata`, and `atlas_idp` when `COMPOSE_PROFILES` includes `bundled-idp` (the default). Then it runs `docker compose up -d`. If you'd rather do it by hand, run those commands yourself. On every later start, `docker compose up -d` alone is enough.

On first start:
- `atlas-init` generates every secret into `./secrets/` (`0700` dir, `0600` files) and never overwrites existing files;
- `atlas-db-init` creates the database roles;
- `atlas-idp-init` (bundled IdP) generates the IdP's internal CA and TLS certificate and writes its configuration ([details](#the-bundled-identity-provider));
- `atlas-idp-bootstrap` (bundled IdP) sets Kanidm up for Atlas: the OIDC client, the console's service account, the role groups and their sign-in policies. It writes what `atlas-api` needs into `./secrets/atlas-idp/`. You set no OIDC secret by hand ([details](#the-idp-bootstrap)).

Then `atlas-migrate` creates the schema and `atlas-api` starts. `atlas-api` does not start until the bootstrap has succeeded. If it fails, [the bootstrap's log](#if-the-bootstrap-fails) says why. Check it's running:

```bash
curl -s http://127.0.0.1:8080/health
```

The expected output is `{"status":"ok"}`.

Create the first owner. The command prints a one-time enrolment link; open it on your phone or laptop to set a password + TOTP or a passkey:

```bash
docker compose exec atlas-api atlas-admin bootstrap-owner --username <your-name>
```

Finally, make Atlas reachable over HTTPS by choosing an [exposure option](#exposing-atlas). Until you do, Atlas listens on loopback only.

## Configuration reference

Configuration comes from two untracked files, plus optional real environment variables, which win over both:

- **`deploy/.env`**: **non-secret** deployment settings, read by Docker Compose. The template is `.env.example`.
- **`${ATLAS_SECRETS_DIR}/…`**: **secrets**, generated by `atlas-init` if missing. You can pre-create them to supply your own values.

Atlas **refuses to start** on unsafe configuration: a weak or placeholder `SECRET_KEY`, `example.com` URLs, plain-HTTP URLs in production, and so on. The error names the setting but never prints its value ([ADR-004](adr/004-config-and-secrets.md)).

### Deployment settings (`deploy/.env`)

| Variable | Default | Meaning |
|---|---|---|
| `ATLAS_PUBLIC_URL` | *(required)* | Public HTTPS URL of Atlas, e.g. `https://atlas.example.com`. Used for links, cookies, OIDC redirects and the proxy's host allow-list |
| `ATLAS_IDP_PUBLIC_URL` | *(required with the bundled IdP)* | Public HTTPS URL of the bundled IdP, e.g. `https://id.example.com`. Becomes the Kanidm origin and the base of the OIDC issuer. **Don't change it after users enrol passkeys** |
| `ATLAS_BIND_ADDRESS` | `127.0.0.1` | Host address the proxy binds to. Keep loopback when a tunnel or reverse proxy runs on the same host. Use a specific LAN/VPN address or `0.0.0.0` only behind your own TLS proxy and firewall |
| `ATLAS_HTTP_PORT` | `8080` | Host port of the proxy (plain HTTP; TLS is terminated in front) |
| `TZ` | `UTC` | Time zone for container clocks, logs and scheduled jobs (e.g. `Europe/Berlin`). Stored data is always UTC |
| `COMPOSE_PROFILES` | `bundled-idp` | Optional components. Remove `bundled-idp` to [bring your own OIDC](#bring-your-own-oidc-provider). Add `tunnel` to run the bundled Cloudflare Tunnel connector |
| `ATLAS_SECRETS_DIR` | `./secrets` | Host directory for secret files (§[volumes](#volumes-and-files)). An absolute path is recommended in production |
| `ATLAS_BACKUP_DIR` | `./backups` | Host directory for backups and pre-migration dumps |
| `ATLAS_PGDATA_VOLUME` | `atlas_pgdata` | Name of the **external** Docker volume holding Postgres data |
| `ATLAS_IDP_VOLUME` | `atlas_idp` | Name of the **external** Docker volume holding the bundled IdP's data |
| `ATLAS_IDP_FRONT_SUBNET` | `10.249.73.0/28` | Private IPv4 subnet (`/16`–`/29`) of the internal `idp-front` network. Kanidm trusts `X-Forwarded-For` only from it. Change it only if it collides with a network on your host ([how](#changing-the-idp-front-subnet)) |
| `ATLAS_IDP_BACKUP_SCHEDULE` | `0 * * * *` | When Kanidm writes its online backup (cron, UTC: minute hour day month weekday; or 7 fields starting with seconds) |
| `ATLAS_IDP_BACKUP_VERSIONS` | `24` | How many Kanidm online backups to keep in `backups/idp-online/` |
| `ATLAS_IMMICH_PUBLIC_URL` | *(unset)* | Immich's own HTTPS origin, with no path (e.g. `https://immich.example.com`), different from both hostnames above. When set, the [IdP bootstrap](#the-idp-bootstrap) creates Immich's OAuth2 client with exactly the redirect URIs under [Connecting Immich](#connecting-immich). Bundled IdP only |
| `ATLAS_RATE_LIMIT_IDP_AUTH` | `30r/m` | Proxy rate limit per client IP for credential submissions to the bundled IdP (Kanidm's own lockout is per account) |
| `ATLAS_IMAGE_TAG` | the release you checked out | Atlas image tag. Pin it, and change it only when [upgrading](#upgrading) |
| `ATLAS_REAL_IP_HEADER` | `X-Forwarded-For` | Header carrying the client IP from the component in front. Set `CF-Connecting-IP` when using the Cloudflare Tunnel |
| `ATLAS_TRUSTED_PROXY_CIDRS` | *(empty)* | Extra peers allowed to set `ATLAS_REAL_IP_HEADER` (comma-separated IPs/CIDRs). Loopback is always trusted, and with a **loopback** `ATLAS_BIND_ADDRESS` so is the Docker gateway. With **any other bind this is required**, and the proxy refuses to start without it: Docker's userland proxy makes every connection arrive from the gateway, so it isn't trusted implicitly ([ADR-003](adr/003-internet-exposure.md) §1) |
| `ATLAS_MAX_BODY_SIZE` | `10m` | Max request body at the proxy (raised by the file modules in First modules) |
| `ATLAS_RATE_LIMIT_AUTH` | `10r/m` | Proxy rate limit per client IP for authentication endpoints |
| `ATLAS_RATE_LIMIT_API` | `20r/s` | Proxy rate limit per client IP for the rest of `/api/` |
| `ATLAS_BACKUP_KEEP_DAILY` | `7` | Daily backups kept by `atlas-backup` |
| `ATLAS_BACKUP_KEEP_WEEKLY` | `4` | Weekly backups kept by `atlas-backup` |

| Variable | Default | Meaning |
|---|---|---|

| `ATLAS_IDP_ADMIN_TOKEN` | bundled: *written by the IdP bootstrap* to `secrets/atlas-idp/idp.env` | Service-account token the console uses to call the IdP admin API. **Required with the bundled IdP** (`atlas-api` refuses to start without it; an install that has run the bootstrap already has it). ## Volumes and files

| What | Default location | Created by | Back up? | Survives `down -v`? |
|---|---|---|---|---|
| Postgres data | Docker volume `atlas_pgdata` (external) | `install.sh` / you | Via `atlas-backup` | ✓ |
| Bundled IdP data | Docker volume `atlas_idp` (external) | `install.sh` / you | Via `atlas-backup` | ✓ |
| Kanidm's admin socket | Docker volume `atlas_idp-admin` (not external) | Compose | No: it holds only a socket | Removed by `down -v`, and recreated empty. Never run `down -v` anyway |
| Secrets | `./secrets/` → `atlas/app.env`, `atlas/connectors.env`, `postgres/password`; bundled IdP: `idp-ca/` (internal CA), `idp/` (key, certificate, `server.toml`), `idp-trust/` (CA certificate), `atlas-idp/` (what the [IdP bootstrap](#the-idp-bootstrap) writes for `atlas-api`: `idp.env`, `groups.json`, `bootstrap.json`; the directory also exists, empty, in BYO mode), `idp-clients/` (Immich's client secret) | `atlas-init`, `atlas-idp-init` (missing files only), `atlas-idp-bootstrap` (its own files) | **Yes**, separately and encrypted. `atlas-idp/idp.env` is regenerated by the bootstrap if it is lost, but back it up with the rest | ✓ (host dir) |
| Backups | `./backups/` → `atlas-<timestamp>/`; bundled IdP: `idp-online/` (Kanidm's online backups), `idp-restore/` (staged for a restore) | `atlas-backup`, `atlas-migrate`, the `idp` service | Copy off-host | ✓ (host dir) |
| Config | `deploy/.env` | You | Yes | ✓ |

**Protecting the secrets directory is your job.** Keep it on an encrypted disk if you can, back it up separately from the database dumps, and never commit it. The repo's `.gitignore` already excludes it.

## Exposing Atlas

Atlas publishes one plain-HTTP port, `ATLAS_BIND_ADDRESS:ATLAS_HTTP_PORT` (loopback `8080` by default). Something in front must:

1. terminate **valid TLS** for both hostnames;
2. forward the original `Host` header;
3. pass the client IP in `ATLAS_REAL_IP_HEADER`;
4. not cache `/api/*`.

The design rationale is in [ADR-003](adr/003-internet-exposure.md).

### Option 1 (recommended): Cloudflare Tunnel

No inbound ports, it works behind CGNAT, and it gives you edge TLS, WAF and rate limiting.

**A. Bundled connector (simplest).**
1. In the Cloudflare dashboard, create a tunnel and copy its token.
2. Create the token file:

   ```bash
   mkdir -p secrets/cloudflared && printf 'TUNNEL_TOKEN=%s\n' '<paste-token>' > secrets/cloudflared/tunnel.env && chmod 600 secrets/cloudflared/tunnel.env
   ```

3. Add `tunnel` to `COMPOSE_PROFILES` in `.env` (e.g. `COMPOSE_PROFILES=bundled-idp,tunnel`). Set `ATLAS_REAL_IP_HEADER=CF-Connecting-IP`.
4. In the tunnel's **Public hostnames**, route **both** hostnames to the service `http://atlas-proxy:8080`. The connector runs inside the compose network, so no host port is involved.
5. Run `docker compose up -d`.

**B. A connector you already run on the host.** Point both hostnames at `http://127.0.0.1:8080` (or your `ATLAS_BIND_ADDRESS:ATLAS_HTTP_PORT`). A locally managed `config.yml` looks like this:

```yaml
tunnel: <tunnel-id>
credentials-file: /etc/cloudflared/<tunnel-id>.json
ingress:
  - hostname: atlas.example.com
    service: http://127.0.0.1:8080
  - hostname: id.example.com
    service: http://127.0.0.1:8080
  - service: http_status:404
```

**Recommended Cloudflare settings:**
- **Rate-limiting rules** on `id.example.com` (login paths) and `atlas.example.com/api/auth/*`.
- Managed WAF rules on.
- **Cloudflare Access on admin paths only.** Create an Access application for `atlas.example.com/admin*` and `atlas.example.com/api/v1/admin/*`, with a policy allowing only your owner/admin identities.
- **Don't** put Access in front of the rest of Atlas, the IdP or Immich: it breaks the Immich mobile app and OIDC back-channel calls, and it adds a second login for everyone.
- Atlas is secure without Access. Access is defense in depth.

### Option 2: your own reverse proxy

Use this when you already run Caddy, Traefik or nginx with ACME certificates. For example, Caddy on the same host:

```caddyfile
atlas.example.com, id.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

Caddy preserves `Host` and sets `X-Forwarded-For` by default. That matches the default `ATLAS_REAL_IP_HEADER`.

If the proxy runs on **another machine**:
- set `ATLAS_BIND_ADDRESS` to this host's LAN address;
- add the proxy's address to `ATLAS_TRUSTED_PROXY_CIDRS`;
- firewall the port so only the proxy can reach it.

To mimic the admin-path protection of option 1, restrict `/admin*` and `/api/v1/admin/*` at your proxy, for example to VPN or LAN source ranges.

### Option 3: VPN only

Run a VPN (WireGuard or a mesh VPN) and option 2's proxy on the VPN interface. You still need **trusted certificates** for both hostnames (for example ACME with the DNS-01 challenge), because passkeys and the Immich mobile app require them. Every family device needs the VPN client.

### Hairpin / split DNS

The Immich server (and Atlas, with BYO OIDC) must reach the IdP's **public** URL from inside your network. If your router can't route your own public hostname back to your host ("hairpin NAT"), add a local DNS override that resolves `id.example.com` to your reverse proxy. With the Cloudflare Tunnel this usually works without changes, because traffic leaves and re-enters through Cloudflare.

## The bundled identity provider

With `COMPOSE_PROFILES=bundled-idp` (the default), the stack runs [Kanidm](https://kanidm.github.io/kanidm/stable/) 1.12 as the `idp` service ([ADR-001](adr/001-identity.md)). atlas-proxy serves it at `ATLAS_IDP_PUBLIC_URL` and re-encrypts every request to it over TLS, verified against an internal CA.

**Services:**

| Service | What it does |
|---|---|
| `atlas-idp-init` | One-shot, as root and with no network, like `atlas-init`. Writes the internal CA, the IdP's TLS key and certificate, and Kanidm's `server.toml`, and gives the IdP's two volumes (database, admin socket) and its backup directories to the IdP's user |
| `idp` | Kanidm, pinned by digest. Runs as **uid/gid 10002** (the upstream image would run as root), with a read-only root filesystem. Its healthcheck verifies TLS (`kanidmd scripting healthcheck -v`) |
| `atlas-idp-bootstrap` | One-shot, on every `up`, after `idp` is healthy and before `atlas-api`: sets Kanidm up for Atlas ([the IdP bootstrap](#the-idp-bootstrap)). Runs as uid 10002 with every capability dropped, a read-only root filesystem and only the `idp-back` network. It mounts Kanidm's admin socket (read-only), never its database and never the Docker socket |

**Networks.** Neither network has internet access:

| Network | Members | Purpose |
|---|---|---|
| `default` | every Atlas service | As before. atlas-proxy's default route and Docker gateway stay here, so the [trusted peers](#configuration-reference) are unchanged |
| `idp-front` (internal, subnet `ATLAS_IDP_FRONT_SUBNET`) | atlas-proxy, idp | The proxy's path to Kanidm. Kanidm trusts `X-Forwarded-For` from this subnet only. atlas-proxy overwrites that header with the verified client address, so Kanidm's logs and lockout see the real client |
| `idp-back` (internal) | atlas-api, atlas-idp-bootstrap, idp | The back-channel to Kanidm: the bootstrap's calls today, the OIDC token exchange from Phase 5c. Kanidm trusts nothing on it |

**What the host can reach on `idp-front`.** Nothing. Docker normally gives the host an address on every bridge network (the network's gateway), and on `idp-front` that address would lie inside the subnet Kanidm trusts: a program on the host could connect straight to Kanidm and name any client address in `X-Forwarded-For`. So `idp-front` is created with the bridge option `com.docker.network.bridge.inhibit_ipv4`, which leaves the host without an address or a route in that subnet:

- from the host, a connection to Kanidm's `idp-front` address fails. To reach the IdP from the host, go through atlas-proxy (`ATLAS_IDP_PUBLIC_URL`), like every other client;
- atlas-proxy and `idp` reach each other as before, by service name;
- `docker compose exec` and `docker compose logs` still work, because they don't use the network.

To check it on a running stack (the project is named `atlas` unless you changed it), this prints `true`:

```bash
docker network inspect atlas_idp-front --format '{{index .Options "com.docker.network.bridge.inhibit_ipv4"}}'
```

This covers the host's own network stack. Anyone who can run Docker commands on the host can still attach a container to any network, as with every Docker setup, so keep access to the Docker socket limited to administrators.

**In BYO mode**, atlas-proxy still joins `idp-front`, so that network exists either way:

- `ATLAS_IDP_FRONT_SUBNET` is still used and can still collide with a network of yours. The fix is the same: [change it](#changing-the-idp-front-subnet);
- `secrets/idp-trust/` still exists, because atlas-proxy mounts it. `atlas-init` creates it (root, `0755`) and it stays empty: no CA or certificate is generated without the bundled IdP.

**Configuration.** All of Kanidm's settings are in `secrets/idp/server.toml`. `atlas-idp-init` rewrites it from `deploy/.env` on every start, so don't edit it. It holds no secrets. Never add `KANIDM_*` variables to the compose file: they override `server.toml`, and `KANIDM_TRUST_X_FORWARDED_FOR=true` makes Kanidm trust every client's address.

**Files** (with `--chown`, as `atlas-idp-init` runs it):

| Path | Contents | Seen by | Owner, mode |
|---|---|---|---|
| `secrets/idp-ca/ca.key`, `ca.pem` | The internal CA. Never rotated automatically | **no running service** | root, `0600` (directory `0700`) |
| `secrets/idp/server.key`, `chain.pem`, `server.toml` | Kanidm's TLS key, its certificate + the CA certificate, its config | `idp`, read-only | root, group 10002, `0440` (directory `0750`) |
| `secrets/idp-trust/ca.pem` | The CA certificate only (public). The directory also exists, empty, in BYO mode | atlas-proxy, atlas-api, atlas-idp-bootstrap | root, `0644` (directory `0755`) |
| `secrets/atlas-idp/idp.env` | `ATLAS_OIDC_CLIENT_SECRET` and `ATLAS_IDP_ADMIN_TOKEN`. **Secret** | atlas-idp-bootstrap (writes), `atlas-api` (read-only) | uid 10002, group 10001, `0640` |
| `secrets/atlas-idp/groups.json` | Each Atlas group's name and Kanidm UUID. Not secret | the same | the same |
| `secrets/atlas-idp/bootstrap.json` | The bootstrap's [completion record](#if-the-bootstrap-fails). Not secret | the same | the same |
| `secrets/atlas-idp/` | The directory: also exists, empty, in BYO mode | | uid 10002, group 10001, `2750` (BYO: root, group 10001, `0750`) |
| `secrets/idp-clients/immich.env` | Immich's OAuth2 client secret, only with `ATLAS_IMMICH_PUBLIC_URL`. **Secret** | atlas-idp-bootstrap (writes); you, with `sudo` | uid 10002, `0600` (directory `0700`) |
| `backups/idp-online/` | Kanidm's online backups (gzip). **They contain every IdP secret** | `idp` (writes), `atlas-backup` (reads) | uid 10002, group 10001, `2750` |
| `backups/idp-restore/` | A backup staged by `atlas-admin restore` | `idp`, read-only | uid 10001, group 10002, `2750` |
| Docker volume `atlas_idp` | Kanidm's database | `idp` | uid 10002, `0700` |
| Docker volume `atlas_idp-admin` | Kanidm's admin socket, nothing else. No data, no backup | `idp`, atlas-idp-bootstrap (read-only) | uid 10002, `0700` |

**The admin socket.** Kanidm has a unix socket for administration that needs no password: whoever can connect to it can reset the password of the built-in `idm_admin` account. The stack keeps it on its own small Docker volume, `atlas_idp-admin` (`<project>_idp-admin`, where the project is `atlas` unless you changed it), and `server.toml` points Kanidm there (`adminbindpath`). The volume holds the socket and nothing else:

- the directory belongs to uid 10002 with mode `0700`, so only Kanidm's own user, and root with the `DAC_OVERRIDE` capability, can connect. A container that mounts this volume, even read-only, reaches the socket as uid 10002 and no other user does. That is how `atlas-idp-bootstrap` uses it, without ever mounting Kanidm's database;
- it is an ordinary project volume, not an external one like `atlas_idp`: Compose creates it, `atlas-idp-init` prepares it on every start, and Kanidm recreates the socket on every start. It holds no data, so it needs no backup and `install.sh` does not create it;
- the bootstrap is the only Atlas service that uses the socket. It resets `idm_admin`'s password with it to get a session, and disables the account again when it is done.

### The IdP bootstrap

`atlas-idp-bootstrap` runs on every `docker compose up -d`, after `idp` is healthy and before `atlas-api`. It signs in to Kanidm as `idm_admin` and makes sure that everything Atlas needs is there. Each step reads first and changes only what differs, and says what it did in one line of names, UUIDs and `created`, `kept` or `updated`. **Its log never holds a secret:**

```bash
docker compose logs atlas-idp-bootstrap
```

| What | Detail |
|---|---|
| Groups | `atlas_users`, the five role groups `atlas_role_owner`, `atlas_role_admin`, `atlas_role_adult`, `atlas_role_child` and `atlas_role_guest` (each a member of `atlas_users`), and `immich_users` with Immich. Atlas maps groups by UUID, from `secrets/atlas-idp/groups.json`, never by name |
| Sign-in policies | Owner and admin need a second factor (`mfa`) and sign out after 8 hours. Adults need a second factor. Children and guests may use a password alone. Kanidm applies the strictest policy of a person's groups, so `idm_all_persons` is lowered to `any` only after all five role groups carry theirs, and the bootstrap checks that order itself |
| The console's account | The service account `atlas-console`, managed by `idm_admins` and a member of `idm_people_admins`, with exactly one API token labelled `atlas-console`. It manages the five role groups and `immich_users`: [the console's limited rights](#the-consoles-limited-rights) |
| Atlas's OIDC client | `atlas`, with `https://atlas.example.com/api/v1/auth/callback` as its landing URL and its only redirect URL, strict redirect matching, PKCE required, the legacy RS256 signing off, and the scopes `openid profile groups` for `atlas_users` |
| Immich's OIDC client | Only with `ATLAS_IMMICH_PUBLIC_URL` set: [Connecting Immich](#connecting-immich) |
| Files | `secrets/atlas-idp/idp.env` (the client secret and the console token, for `atlas-api`), `groups.json`, `bootstrap.json`, and `secrets/idp-clients/immich.env` |

**Children and guests need a password of at least 15 characters.** That is Kanidm's rule for an account without a second factor, and the group setting that should lower it did not. A passphrase or a passkey satisfies it. People with a second factor need 10.

**Nothing is entered by hand.** The OIDC client secret comes from Kanidm and is written into `idp.env`, which `atlas-api` loads last, so it wins over an `ATLAS_OIDC_CLIENT_SECRET` you set in `secrets/atlas/app.env` before. You can delete that line. If a stored value and Kanidm ever disagree, Kanidm's wins.

**A client you made by hand is adopted.** If a client named `atlas` or `immich` already exists in Kanidm (you created it while trying things out), the bootstrap keeps it and enforces its settings: the landing URL, strict redirects, PKCE, no legacy signing. It **removes every redirect URI other than the documented ones**, and reads its secret. On `--verify` runs only, it also removes scope maps it did not set, on those two clients. Other clients are never touched.

**`idm_admin` is disabled again** whenever the bootstrap is done, whether it succeeded or failed, and also when it is stopped by SIGTERM. The password the bootstrap gets for it and its session never touch a disk or a log. Only a SIGKILL or a power failure in the middle of a run can leave the account enabled, with a password nobody has, until the next `up`, which disables it again.

**The fast path.** When nothing changed, a run does not reset any password and does not sign in. It skips all the steps above when the last run completed, the settings it depends on are unchanged, the stored console token works, and every group UUID in `groups.json` still matches Kanidm (as the console sees them: it cannot see `atlas_users`, which `--verify` checks). It still sends `DisableAccount` for `idm_admin` over the socket, and if that fails, the run fails. The fast path cannot see someone changing a client or a policy in Kanidm; `--verify` can:

```bash
docker compose run --rm atlas-idp-bootstrap atlas-admin idp-bootstrap --verify
```

`--verify` always does the full run and repairs any difference. Everything it finds right is logged as `kept`.

#### The console's limited rights

The console's API token (`ATLAS_IDP_ADMIN_TOKEN`) can act on people and on six groups, and on nothing else. This matters if the token ever leaks.

- **It can:** create, read, delete and disable persons; issue a credential-reset link (and wipe a person's credential); add and remove members of the five role groups and `immich_users`. That is enough to make anyone an owner inside Atlas, so treat the token like an owner's password: it is only readable by `atlas-api` and the people with access to `secrets/atlas-idp/`.
- **It cannot:** change who the Kanidm administrators are, change a role group's sign-in policy or session length, change `idm_all_persons`, `atlas_users` or any other group, create, rename or delete a group, hand a group over to someone else, see or change the OAuth2 clients or their secrets, issue a token for itself or for anyone, set a password directly, or act on `idm_admin` or on its own account.

It gets this through Kanidm's `entry_managed_by`, not through `idm_group_admins`: that group would let it change the members of every group that is not high-privilege, including `atlas_users` and `idm_all_persons`, and delete or rename them. A test pins both lists against the real Kanidm, so a Kanidm upgrade that widens the token's rights fails CI.

**`--verify` removes anything that is not a person from the six groups** (a service account or a group someone added by hand). It logs the group, the name and the UUID, nothing else. Persons are never removed.

**Upgrading from an earlier pre-release:** the next `docker compose up -d` runs one full bootstrap (a few seconds) that sets the managers, checks each one, and only then removes the console from `idm_group_admins`. `atlas-api` waits for it as usual. If a run stops in between, the console keeps its old rights until the next run finishes the job. Nothing to change by hand.

**Disabling a person.** Disabling an account in Kanidm (it sets `account_expire`) stops their existing Kanidm sessions and new logins, but **clearing it makes the old sessions valid again** until they reach their own lifetime (up to 24 hours, 8 hours for owners and admins). Changing the person's credential ends them for good. So when you disable someone because the account may be compromised, also issue a reset link, so that they set a new password and second factor: the old sessions then stay refused. A reset link cannot be revoked, and issuing a new one does not cancel an older one: each stays valid until it is used or expires, so keep the lifetime short.

#### Reset links

A reset link is what a person opens to set their password and second factor (or a passkey) without any mail. The console shows it once, as a link and a QR code, for in-person hand-over.

- **It is a secret.** Anyone who has it can set that person's credentials. Atlas never logs it and shows nothing of it in an error; treat a printed one like a password.
- **The host is `ATLAS_IDP_PUBLIC_URL`**, in the form `https://id.example.com/ui/reset?token=…`, never an internal address.
- **It lives 15 minutes by default, and 5 minutes to 1 hour at most.** The console and the CLI refuse anything else instead of rounding it. A person only has to open the link inside that time: what they are doing after they opened it (setting a password, scanning a code) may take longer.
- **It cannot be revoked, and a new link does not cancel an older one.** Kanidm has no call for either (checked on 1.12.0). Each link works until it is used or expires. Deleting the person ends every link they have. This is why the lifetime is short: if a link may have been seen by someone else, issue a new one only after the old one has expired, or delete and recreate the person.
- **A disabled person gets no link.** Enable them first.
- **Kanidm's own log records the link when it is opened**, because the request line holds the address (`docker compose logs idp`). No Atlas service logs it, and a test checks every service's log, but that one line is Kanidm's. So whoever can read `docker compose logs idp` can read the links that were opened in the last hour: that is the host's administrator, who could issue links anyway. Keep the logs of the host as private as the secrets directory.

#### If the bootstrap fails

`atlas-api` does not start until the bootstrap has succeeded, **every time, not only on the first install**. Compose can't enforce that by itself (a dependency that BYO mode doesn't have may only be declared optional, and Compose then starts `atlas-api` anyway after a failure), so the bootstrap keeps a completion record, `secrets/atlas-idp/bootstrap.json`:

- every run, the fast path included, writes `complete: false` first, and `complete: true` as its very last act;
- `atlas-api` (bundled IdP only) refuses to start unless the record says `complete: true` for this release's bootstrap version. A failure, a signal, or a kill leaves `false`, so an older `idp.env` on disk never lets the API start on an unfinished setup.

What you see: `docker compose up -d` reports `atlas-api` as failed and `atlas-proxy` stays down, and `atlas-api`'s log says:

```
ATLAS_IDP_BOOTSTRAP_RECORD: the bundled IdP's bootstrap has not completed (its last run failed); read `docker compose logs atlas-idp-bootstrap`, fix what it reports, then run `docker compose up -d` again
```

1. Read `docker compose logs atlas-idp-bootstrap`. The last line says which step failed (for example `failed at step login: …`) and why. Common causes: `idp` is not healthy (`docker compose ps`), or `secrets/idp-trust/ca.pem` or the `idp-admin` volume is missing because `atlas-idp-init` did not run.
2. Fix it, then run `docker compose up -d`. The next run is always a full one.
3. `atlas-api` is restarting by itself and starts as soon as the record is complete, but the `up -d` that ran the fixed bootstrap may still report it as unhealthy, because it looks while the container is restarting. If so, wait for `docker compose ps` to show `atlas-api` healthy (a few seconds up to a minute), then run `docker compose up -d` once more: that starts `atlas-proxy`.

#### Rotating the console token

```bash
docker compose run --rm atlas-idp-bootstrap atlas-admin idp-bootstrap --rotate-console-token
```

```bash
docker compose restart atlas-api
```

The command issues a new token, checks that Kanidm accepts it, writes it to `idp.env`, and only then deletes the old one, so a working token is stored at every moment. It leaves exactly one token. It ends by telling you to restart `atlas-api`, which holds the old token until then.

**Kanidm keeps accepting a token for up to five minutes after it was deleted** (checked on 1.12.0: a token younger than 300 seconds still works, an older one stops at once). So the old token works for up to five minutes after a rotation, and the command can't shorten that. If you rotate because a token leaked, treat it as valid for five more minutes.

**Renewing the IdP's certificate.** The internal certificate is valid for three years. `atlas-idp-init` warns 60 days before it expires. To issue a new one from the same CA (nothing needs to change in atlas-proxy, which trusts the CA), run:

```bash
docker compose run --rm atlas-idp-init atlas-admin init --secrets-dir=/secrets --backup-dir=/backups --chown --idp-data-dir=/idp-data --idp-admin-dir=/idp-admin --rotate-idp-cert
```

Then restart the IdP:

```bash
docker compose restart idp
```

### Changing the idp-front subnet

The default `10.249.73.0/28` lies outside Docker's default address pools and the ranges home routers usually use. If `docker compose up` reports that a pool overlaps, or the subnet is used elsewhere on your network, pick another private `/28`, e.g. `10.249.74.0/28`. Set it as `ATLAS_IDP_FRONT_SUBNET` in `deploy/.env`, then recreate the stack (never `down -v`):

```bash
docker compose down
```

```bash
./install.sh
```

`atlas-idp-init` writes the new subnet into Kanidm's `server.toml` on that start.

## Bring your own OIDC provider

If you already run Authentik, Keycloak, Kanidm, Authelia, Pocket ID or similar:

1. In `.env`, remove `bundled-idp` from `COMPOSE_PROFILES`, and leave `ATLAS_IDP_PUBLIC_URL` unset.
2. In your IdP, create a confidential OIDC client:
   - redirect URI `https://atlas.example.com/api/v1/auth/callback`;
   - scopes `openid profile`;
   - PKCE S256 enabled.
3. Put `ATLAS_OIDC_ISSUER`, `ATLAS_OIDC_CLIENT_ID` and `ATLAS_OIDC_CLIENT_SECRET` in `secrets/atlas/app.env`. `ATLAS_IDENTITY_ADMIN` defaults to `manual`.
4. Run `docker compose up -d`, then `atlas-admin bootstrap-owner`. It prints a **link code** URL; open it and sign in at your IdP to bind your account.

**What changes with BYO:**
- You create identities and reset credentials in your IdP.
- In the Atlas console, admins create the Atlas user (role, modules) and hand out a one-time link code.
- Atlas never matches accounts by email or username.

**Requirements on your IdP:**
- It must honour `prompt=login` / `max_age` and return `auth_time`. Without them, admin actions that need step-up are refused.
- It must enforce MFA for the people you make owner or admin.

## Connecting Immich

Immich runs as its own stack (see Immich's docs). Atlas connects to it in two ways:

1. **SSO.** In Immich's OAuth settings, use the same IdP:
   - Bundled IdP: set `ATLAS_IMMICH_PUBLIC_URL=https://immich.example.com` in `deploy/.env` (Immich's own HTTPS origin, no path) and run `docker compose up -d`. The [IdP bootstrap](#the-idp-bootstrap) creates the client `immich`, and the group `immich_users`, whose members are the only people allowed to sign in to it. Read the client secret on the host (the file is `0600`, owned by uid 10002 in a `0700` directory, so it needs `sudo`):

     ```bash
     sudo cat secrets/idp-clients/immich.env
     ```

     It holds one line, `OAUTH_CLIENT_SECRET=…`: paste the value into Immich's OAuth settings. Without `ATLAS_IMMICH_PUBLIC_URL` no Immich client exists.
   - The IdP client is confidential, with strict redirect URIs. The bootstrap sets its redirect URIs to exactly these, and removes any other:
     - `https://immich.example.com/auth/login`;
     - `https://immich.example.com/user-settings`;
     - `app.immich:///oauth-callback` (the mobile app; Kanidm accepts it as an opaque origin).
   - Issuer: `https://id.example.com/oauth2/openid/immich`.
   - Signing algorithm: **ES256** (required, confirmed). Immich's default, RS256, fails with "Failed to finish oauth".
   - Token endpoint auth: `client_secret_post` (confirmed).
   - Immich's mobile redirect override is **not** needed (tested with Immich 3.3.5 and Kanidm 1.12.0).
   - These settings are validated in [ADR-001 → Spike results](adr/001-identity.md#spike-results).
2. **Connector.** In the Atlas admin console → Connectors → Immich, enter the Immich URL. Health appears there, and family members with **Immich access** get a "Photos (Immich)" link.
   - With the bundled IdP, that toggle also controls whether the IdP lets them log in to Immich.

## Backup and restore

**Back up:** dumps the database into `ATLAS_BACKUP_DIR/atlas-<timestamp>/`, rotating per the `ATLAS_BACKUP_KEEP_*` settings. With the bundled IdP it also copies Kanidm's newest online backup into the set as `idp.json.gz` (mode `0600`). The manifest records that backup's Kanidm version and age. Kanidm writes an online backup every hour by default (`ATLAS_IDP_BACKUP_SCHEDULE`). Right after the first start there isn't one yet: `atlas-backup` then says so in a warning and still backs up the database.

```bash
docker compose run --rm atlas-backup
```

**Schedule it** with whatever your host uses. For example, a nightly cron entry for the user that runs Docker:

```
15 3 * * * cd /path/to/atlas/deploy && docker compose run --rm atlas-backup >> backups/backup.log 2>&1
```

**Copy backups and the secrets directory off the host** (to another disk, a NAS or encrypted cloud storage). A backup on the same disk is not a backup.

**Restore** (into the same or a fresh host):
1. Install as in the quick start, but **restore your old `secrets/` directory first**, so `atlas-init` doesn't generate new secrets.
2. Stop the API:

   ```bash
   docker compose stop atlas-api
   ```

3. Restore the database from a backup set:

   ```bash
   docker compose run --rm atlas-backup atlas-admin restore --from /var/backups/atlas/atlas-<timestamp> --yes
   ```

   With the bundled IdP this first checks that the backup's Kanidm version is the one this stack runs. **Kanidm only restores into the same version**: on a mismatch it stops before changing anything, and you restore with the Atlas release (idp image) the backup was made with. It then restores the database, stages the IdP backup in `backups/idp-restore/`, and prints the IdP steps, which look like this:

   ```bash
   docker compose stop idp
   ```

   ```bash
   docker compose run --rm --no-deps idp /sbin/kanidmd database restore -c /etc/atlas-idp/server.toml /restore/atlas-<timestamp>-idp.json.gz
   ```

   ```bash
   docker compose start idp
   ```

   Kanidm's restore is offline (the `idp` service stopped). It decompresses the file only because the name ends in `.gz`, so keep that name. Afterwards delete the staged file in `backups/idp-restore/`: it contains every IdP secret.

4. Start the stack:

   ```bash
   docker compose up -d
   ```

**Test a restore** at least once, on a scratch host or with a different `ATLAS_PGDATA_VOLUME` / `ATLAS_IDP_VOLUME` name.

## Upgrading

1. Read the [release notes](../CHANGELOG.md) for breaking changes, especially the release's **Upgrade notes** subsection.
2. Take a backup:

   ```bash
   docker compose run --rm atlas-backup
   ```

3. Update the checkout or bump `ATLAS_IMAGE_TAG` in `.env`, then pull:

   ```bash
   git pull && docker compose pull
   ```

4. Start the new version:

   ```bash
   docker compose up -d
   ```

`atlas-migrate` takes its own pre-migration dump, applies the migrations, and only then lets `atlas-api` start. If a migration fails, the API stays down and the log says why. Roll back by restoring the pre-migration dump and setting `ATLAS_IMAGE_TAG` back to the previous version. Migrations are forward-only.

Again: stop with `docker compose down`, **never** `docker compose down -v`.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| `atlas-api` exits with `SECRET_KEY …` | Weak, placeholder or missing key. Delete the bad line from `secrets/atlas/app.env` and re-run `docker compose up -d` to regenerate it, or set your own value |
| `atlas-api` exits mentioning `example.com` or `https` | You haven't set real HTTPS URLs in `.env` |
| `atlas-api` exits with `ATLAS_IDP_BOOTSTRAP_RECORD: the bundled IdP's bootstrap has not completed`, or `ATLAS_ENV_FILES: file not found: …/idp.env` | The [IdP bootstrap](#if-the-bootstrap-fails) failed, or has not run. Read `docker compose logs atlas-idp-bootstrap`, fix what it reports and run `docker compose up -d` again (twice, if the first reports `atlas-api` unhealthy while it is restarting) |
| `external volume "atlas_pgdata" not found` | Run `./install.sh`, or `docker volume create atlas_pgdata` (and `atlas_idp`) |
| `Pool overlaps with other one on this address space` | `ATLAS_IDP_FRONT_SUBNET` collides with another network: [change it](#changing-the-idp-front-subnet) |
| atlas-proxy: `ATLAS_IDP_PUBLIC_URL is set but the internal CA certificate … is missing` | `ATLAS_IDP_PUBLIC_URL` is set without the `bundled-idp` profile. Enable the profile, or unset the URL for BYO |
| `atlas-admin init: ATLAS_IDP_PUBLIC_URL is not set` | The `bundled-idp` profile is on without `ATLAS_IDP_PUBLIC_URL`. Set it, or remove the profile for BYO |
| `atlas-admin restore: the IdP data in this backup is from Kanidm …` | The backup was made with another Kanidm version. Restore with the Atlas release it came from |
| Login loops or "invalid issuer" | `ATLAS_IDP_PUBLIC_URL` / `ATLAS_OIDC_ISSUER` doesn't exactly match the URL users reach, or the front proxy isn't forwarding `Host` |
| Passkey enrolment fails | The IdP isn't on HTTPS with a trusted certificate, or its hostname changed since enrolment |
| A child or guest can't set a password | Kanidm needs at least 15 characters without a second factor. A passphrase or a passkey works |
| Immich mobile can't log in | Check that Immich's signing algorithm is ES256, that the IdP hostname is reachable from outside, and that no Cloudflare Access policy covers the IdP or Immich |
| Every request appears to come from one IP | `ATLAS_REAL_IP_HEADER` / `ATLAS_TRUSTED_PROXY_CIDRS` don't match your front proxy |
| Locked out of the IdP entirely | Run `docker compose exec atlas-api atlas-admin break-glass --user <owner>` on the host, which gives a one-time 10-minute owner login |
