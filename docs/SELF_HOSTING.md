# Self-hosting Atlas

> **Status: this describes the planned v1 install** ([PLAN-v1](PLAN-v1.md)). The code on `main` today is the pre-v1 prototype and does **not** work this way yet. Variable names and commands may still change before v1.0.0. Until then, treat this page as the target.

> ⚠️ **Never run `docker compose down -v`.**
> The database and IdP volumes are declared external, so Compose can't delete them, but don't rely on that. Use `docker compose down` (without `-v`) to stop the stack.

## Requirements

| Item | Requirement |
|---|---|
| Host | Any 64-bit Linux host (amd64 or arm64): a mini-PC, NAS, VM or small cloud instance |
| Software | Docker Engine with the Compose v2 plugin (a current release) |
| Resources | About 1 GB of free RAM and 2 GB of disk for Atlas + Postgres + the bundled IdP. Immich has its own requirements |
| Domain names | **Two HTTPS hostnames you control**: one for Atlas (e.g. `atlas.example.com`) and one for the identity provider (e.g. `id.example.com`). Immich, if you use it, has its own. See [why two](#why-two-hostnames) |
| TLS | Valid, publicly trusted certificates for those hostnames, provided by whatever sits in front of Atlas (a tunnel or your reverse proxy). Self-signed certificates break passkeys and the Immich mobile app |
| Email | **Not required.** Admins hand out reset/enrolment links in person |

### Why two hostnames

The bundled IdP (Kanidm) is the OIDC issuer for Atlas and Immich. It needs its **own origin**, because it can't run under a sub-path of Atlas.

Pick the IdP hostname once and keep it. **Passkeys are bound to that hostname**, so changing it later forces everyone to re-enrol their passkeys. Password + TOTP survive the change. Details are in [ADR-001](adr/001-identity.md#the-bundled-idps-hostname-and-tls-requirements).

## Quick start

```bash
git clone https://github.com/solahuddeen02/atlas.git
```

```bash
cd atlas/deploy
```

```bash
cp .env.example .env
```

Edit `.env` and set at least `ATLAS_PUBLIC_URL` and `ATLAS_IDP_PUBLIC_URL` to your two HTTPS URLs. Everything else has generic defaults. Then install:

```bash
./install.sh
```

`deploy/install.sh` does two things. It creates the external volumes if they're missing (`docker volume create atlas_pgdata`; `atlas_idp` follows once the bundled IdP lands). Then it runs `docker compose up -d`. If you'd rather do it by hand, run those commands yourself. On every later start, `docker compose up -d` alone is enough.

On first start, `atlas-init`:
- generates every secret into `./secrets/` (`0700` dir, `0600` files) and never overwrites existing files;
- creates the database roles;
- generates the IdP's internal TLS certificate;
- bootstraps the bundled IdP.

Then `atlas-migrate` creates the schema and `atlas-api` starts. Check it's running:

```bash
curl -s http://127.0.0.1:8080/health
```

The expected output is `{"status":"ok"}`.

Create the first owner. The command prints a one-time enrolment link; open it on your phone or laptop to set a password + TOTP or a passkey:

```bash
docker compose exec atlas-api atlas-admin bootstrap-owner --username <your-name>
```

Finally, make Atlas reachable over HTTPS by choosing an [exposure option](#exposing-atlas). Until you do, Atlas listens on loopback only.

## Configuration reference

Configuration comes from two untracked files, plus optional real environment variables, which win over both:

- **`deploy/.env`**: **non-secret** deployment settings, read by Docker Compose. The template is `.env.example`.
- **`${ATLAS_SECRETS_DIR}/…`**: **secrets**, generated by `atlas-init` if missing. You can pre-create them to supply your own values.

Atlas **refuses to start** on unsafe configuration: a weak or placeholder `SECRET_KEY`, `example.com` URLs, plain-HTTP URLs in production, and so on. The error names the setting but never prints its value ([ADR-004](adr/004-config-and-secrets.md)).

### Deployment settings (`deploy/.env`)

| Variable | Default | Meaning |
|---|---|---|
| `ATLAS_PUBLIC_URL` | *(required)* | Public HTTPS URL of Atlas, e.g. `https://atlas.example.com`. Used for links, cookies, OIDC redirects and the proxy's host allow-list |
| `ATLAS_IDP_PUBLIC_URL` | *(required with the bundled IdP)* | Public HTTPS URL of the bundled IdP, e.g. `https://id.example.com`. Becomes the Kanidm origin and the base of the OIDC issuer. **Don't change it after users enrol passkeys** |
| `ATLAS_BIND_ADDRESS` | `127.0.0.1` | Host address the proxy binds to. Keep loopback when a tunnel or reverse proxy runs on the same host. Use a specific LAN/VPN address or `0.0.0.0` only behind your own TLS proxy and firewall |
| `ATLAS_HTTP_PORT` | `8080` | Host port of the proxy (plain HTTP; TLS is terminated in front) |
| `TZ` | `UTC` | Time zone for container clocks, logs and scheduled jobs (e.g. `Europe/Berlin`). Stored data is always UTC |
| `COMPOSE_PROFILES` | `bundled-idp` | Optional components. Remove `bundled-idp` to [bring your own OIDC](#bring-your-own-oidc-provider). Add `tunnel` to run the bundled Cloudflare Tunnel connector |
| `ATLAS_SECRETS_DIR` | `./secrets` | Host directory for secret files (§[volumes](#volumes-and-files)). An absolute path is recommended in production |
| `ATLAS_BACKUP_DIR` | `./backups` | Host directory for backups and pre-migration dumps |
| `ATLAS_PGDATA_VOLUME` | `atlas_pgdata` | Name of the **external** Docker volume holding Postgres data |
| `ATLAS_IDP_VOLUME` | `atlas_idp` | Name of the **external** Docker volume holding the bundled IdP's data |
| `ATLAS_IMAGE_TAG` | the release you checked out | Atlas image tag. Pin it, and change it only when [upgrading](#upgrading) |
| `ATLAS_REAL_IP_HEADER` | `X-Forwarded-For` | Header carrying the client IP from the component in front. Set `CF-Connecting-IP` when using the Cloudflare Tunnel |
| `ATLAS_TRUSTED_PROXY_CIDRS` | *(empty)* | Extra peers allowed to set `ATLAS_REAL_IP_HEADER` (comma-separated IPs/CIDRs). Loopback is always trusted, and with a **loopback** `ATLAS_BIND_ADDRESS` so is the Docker gateway. With **any other bind this is required**, and the proxy refuses to start without it: Docker's userland proxy makes every connection arrive from the gateway, so it isn't trusted implicitly ([ADR-003](adr/003-internet-exposure.md) §1) |
| `ATLAS_MAX_BODY_SIZE` | `10m` | Max request body at the proxy (raised by the file modules in First modules) |
| `ATLAS_RATE_LIMIT_AUTH` | `10r/m` | Proxy rate limit per client IP for authentication endpoints |
| `ATLAS_RATE_LIMIT_API` | `20r/s` | Proxy rate limit per client IP for the rest of `/api/` |
| `ATLAS_BACKUP_KEEP_DAILY` | `7` | Daily backups kept by `atlas-backup` |
| `ATLAS_BACKUP_KEEP_WEEKLY` | `4` | Weekly backups kept by `atlas-backup` |

### Application settings

These are normally left at their defaults or generated. Secrets live in `${ATLAS_SECRETS_DIR}/atlas/app.env`. Non-secret ones can go in either file.

| Variable | Default | Meaning |
|---|---|---|
| `ATLAS_ENV` | `production` | `production`, `development` or `test`. Production enforces HTTPS URLs, `Secure` cookies, docs off and CORS off. **Leaving it unset means production** |
| `SECRET_KEY` | *(generated)* | Signs sessions and CSRF tokens and derives internal keys. ≥ 32 random bytes. Placeholders are rejected. Rotating it signs everyone out |
| `SECRET_KEY_PREVIOUS` | *(unset)* | During rotation, the old key, accepted for verification only |
| `DATABASE_URL` | *(generated)* | `postgresql+psycopg://atlas_app:…@postgres:5432/atlas`. The API's DML-only role |
| `ATLAS_MIGRATOR_DATABASE_URL` | *(generated)* | Connection for the `atlas_migrator` role (DDL), used only by `atlas-migrate` |
| `ATLAS_ENV_FILES` | `/run/secrets/atlas/app.env,/run/secrets/atlas/connectors.env` | Env files the app loads at startup (in-container paths). Rarely changed |
| `ATLAS_OIDC_ISSUER` | bundled: `${ATLAS_IDP_PUBLIC_URL}/oauth2/openid/atlas` | OIDC issuer URL. Set it to your provider's issuer for BYO |
| `ATLAS_OIDC_CLIENT_ID` | `atlas` | OIDC client ID |
| `ATLAS_OIDC_CLIENT_SECRET` | *(generated with the bundled IdP)* | OIDC client secret. Required for BYO |
| `ATLAS_OIDC_INTERNAL_URL` | bundled: `https://idp:8443` | Optional back-channel base URL for discovery, token and JWKS calls. `iss` is still validated against the public issuer |
| `ATLAS_OIDC_CA_FILE` | bundled: the internal CA under the secrets dir | CA bundle for verifying `ATLAS_OIDC_INTERNAL_URL` |
| `ATLAS_IDENTITY_ADMIN` | bundled: `kanidm`; BYO: `manual` | How the console manages identities. `kanidm` creates/resets people in the IdP. `manual` uses one-time link codes, and you manage credentials in your IdP |
| `ATLAS_IDP_ADMIN_TOKEN` | *(generated with the bundled IdP)* | Service-account token the console uses to call the IdP admin API |
| `ATLAS_STEP_UP_MAX_AGE` | `300` | Seconds a re-authentication stays valid for admin actions |
| `ATLAS_SESSION_IDLE_<ROLE>` / `ATLAS_SESSION_MAX_<ROLE>` | owner/admin `12h`/`7d`; adult and child `14d`/`30d`; guest `1d`/until expiry | Session idle and absolute lifetimes per role (`OWNER`, `ADMIN`, `ADULT`, `CHILD`, `GUEST`) |
| `ATLAS_MODULES` | `hello,immich` (Foundation) | Installed modules to load. Enabling them happens in the admin console |
| `ATLAS_MODULE_<ID>_*` | per module | Non-secret module settings, documented by each module |
| `ATLAS_CONNECTOR_<NAME>_*` | *(unset)* | Connector secrets referenced by name from the console, e.g. `ATLAS_CONNECTOR_IMMICH_API_KEY`. Put them in `${ATLAS_SECRETS_DIR}/atlas/connectors.env` |
| `ATLAS_LOG_LEVEL` | `info` | `debug`, `info`, `warning` or `error` |
| `ATLAS_LOG_FORMAT` | `json` | `json` or `text` |
| `ATLAS_DEV_CORS_ORIGINS` | *(empty)* | Development only: comma-separated origins allowed by CORS (e.g. a Vite dev server). Ignored in production |

The Postgres container reads its superuser password from `${ATLAS_SECRETS_DIR}/postgres/password` through the image's `POSTGRES_PASSWORD_FILE` variable. Atlas never uses the superuser at runtime.

## Volumes and files

| What | Default location | Created by | Back up? | Survives `down -v`? |
|---|---|---|---|---|
| Postgres data | Docker volume `atlas_pgdata` (external) | `install.sh` / you | Via `atlas-backup` | ✓ |
| Bundled IdP data | Docker volume `atlas_idp` (external) | `install.sh` / you | Via `atlas-backup` | ✓ |
| Secrets | `./secrets/` → `atlas/app.env`, `atlas/connectors.env`, `postgres/password`, `idp/` (internal CA + cert) | `atlas-init` (missing files only) | **Yes**, separately and encrypted | ✓ (host dir) |
| Backups | `./backups/` | `atlas-backup`, `atlas-migrate` | Copy off-host | ✓ (host dir) |
| Config | `deploy/.env` | You | Yes | ✓ |

**Protecting the secrets directory is your job.** Keep it on an encrypted disk if you can, back it up separately from the database dumps, and never commit it. The repo's `.gitignore` already excludes it.

## Exposing Atlas

Atlas publishes one plain-HTTP port, `ATLAS_BIND_ADDRESS:ATLAS_HTTP_PORT` (loopback `8080` by default). Something in front must:

1. terminate **valid TLS** for both hostnames;
2. forward the original `Host` header;
3. pass the client IP in `ATLAS_REAL_IP_HEADER`;
4. not cache `/api/*`.

The design rationale is in [ADR-003](adr/003-internet-exposure.md).

### Option 1 (recommended): Cloudflare Tunnel

No inbound ports, it works behind CGNAT, and it gives you edge TLS, WAF and rate limiting.

**A. Bundled connector (simplest).**
1. In the Cloudflare dashboard, create a tunnel and copy its token.
2. Create the token file:

   ```bash
   mkdir -p secrets/cloudflared && printf 'TUNNEL_TOKEN=%s\n' '<paste-token>' > secrets/cloudflared/tunnel.env && chmod 600 secrets/cloudflared/tunnel.env
   ```

3. Add `tunnel` to `COMPOSE_PROFILES` in `.env` (e.g. `COMPOSE_PROFILES=bundled-idp,tunnel`). Set `ATLAS_REAL_IP_HEADER=CF-Connecting-IP`.
4. In the tunnel's **Public hostnames**, route **both** hostnames to the service `http://atlas-proxy:8080`. The connector runs inside the compose network, so no host port is involved.
5. Run `docker compose up -d`.

**B. A connector you already run on the host.** Point both hostnames at `http://127.0.0.1:8080` (or your `ATLAS_BIND_ADDRESS:ATLAS_HTTP_PORT`). A locally managed `config.yml` looks like this:

```yaml
tunnel: <tunnel-id>
credentials-file: /etc/cloudflared/<tunnel-id>.json
ingress:
  - hostname: atlas.example.com
    service: http://127.0.0.1:8080
  - hostname: id.example.com
    service: http://127.0.0.1:8080
  - service: http_status:404
```

**Recommended Cloudflare settings:**
- **Rate-limiting rules** on `id.example.com` (login paths) and `atlas.example.com/api/auth/*`.
- Managed WAF rules on.
- **Cloudflare Access on admin paths only.** Create an Access application for `atlas.example.com/admin*` and `atlas.example.com/api/v1/admin/*`, with a policy allowing only your owner/admin identities.
- **Don't** put Access in front of the rest of Atlas, the IdP or Immich: it breaks the Immich mobile app and OIDC back-channel calls, and it adds a second login for everyone.
- Atlas is secure without Access. Access is defense in depth.

### Option 2: your own reverse proxy

Use this when you already run Caddy, Traefik or nginx with ACME certificates. For example, Caddy on the same host:

```caddyfile
atlas.example.com, id.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

Caddy preserves `Host` and sets `X-Forwarded-For` by default. That matches the default `ATLAS_REAL_IP_HEADER`.

If the proxy runs on **another machine**:
- set `ATLAS_BIND_ADDRESS` to this host's LAN address;
- add the proxy's address to `ATLAS_TRUSTED_PROXY_CIDRS`;
- firewall the port so only the proxy can reach it.

To mimic the admin-path protection of option 1, restrict `/admin*` and `/api/v1/admin/*` at your proxy, for example to VPN or LAN source ranges.

### Option 3: VPN only

Run a VPN (WireGuard or a mesh VPN) and option 2's proxy on the VPN interface. You still need **trusted certificates** for both hostnames (for example ACME with the DNS-01 challenge), because passkeys and the Immich mobile app require them. Every family device needs the VPN client.

### Hairpin / split DNS

The Immich server (and Atlas, with BYO OIDC) must reach the IdP's **public** URL from inside your network. If your router can't route your own public hostname back to your host ("hairpin NAT"), add a local DNS override that resolves `id.example.com` to your reverse proxy. With the Cloudflare Tunnel this usually works without changes, because traffic leaves and re-enters through Cloudflare.

## Bring your own OIDC provider

If you already run Authentik, Keycloak, Kanidm, Authelia, Pocket ID or similar:

1. In `.env`, remove `bundled-idp` from `COMPOSE_PROFILES`, and leave `ATLAS_IDP_PUBLIC_URL` unset.
2. In your IdP, create a confidential OIDC client:
   - redirect URI `https://atlas.example.com/api/v1/auth/callback`;
   - scopes `openid profile`;
   - PKCE S256 enabled.
3. Put `ATLAS_OIDC_ISSUER`, `ATLAS_OIDC_CLIENT_ID` and `ATLAS_OIDC_CLIENT_SECRET` in `secrets/atlas/app.env`. `ATLAS_IDENTITY_ADMIN` defaults to `manual`.
4. Run `docker compose up -d`, then `atlas-admin bootstrap-owner`. It prints a **link code** URL; open it and sign in at your IdP to bind your account.

**What changes with BYO:**
- You create identities and reset credentials in your IdP.
- In the Atlas console, admins create the Atlas user (role, modules) and hand out a one-time link code.
- Atlas never matches accounts by email or username.

**Requirements on your IdP:**
- It must honour `prompt=login` / `max_age` and return `auth_time`. Without them, admin actions that need step-up are refused.
- It must enforce MFA for the people you make owner or admin.

## Connecting Immich

Immich runs as its own stack (see Immich's docs). Atlas connects to it in two ways:

1. **SSO.** In Immich's OAuth settings, use the same IdP:
   - Bundled IdP: create the client with `docker compose exec atlas-api atlas-admin idp-add-client immich --redirect https://immich.example.com/auth/login --redirect https://immich.example.com/user-settings --redirect https://immich.example.com/api/oauth/mobile-redirect`. It prints the client secret once.
   - Issuer: `https://id.example.com/oauth2/openid/immich`.
   - Signing algorithm: ES256.
   - Token endpoint auth: `client_secret_post`.
   - Mobile redirect override: `https://immich.example.com/api/oauth/mobile-redirect`.
   - These are the settings the spike validates. ADR-001 records the final values.
2. **Connector.** In the Atlas admin console → Connectors → Immich, enter the Immich URL. Health appears there, and family members with **Immich access** get a "Photos (Immich)" link.
   - With the bundled IdP, that toggle also controls whether the IdP lets them log in to Immich.

## Backup and restore

**Back up:** dumps the database and the IdP into `ATLAS_BACKUP_DIR`, rotating per the `ATLAS_BACKUP_KEEP_*` settings:

```bash
docker compose run --rm atlas-backup
```

**Schedule it** with whatever your host uses. For example, a nightly cron entry for the user that runs Docker:

```
15 3 * * * cd /path/to/atlas/deploy && docker compose run --rm atlas-backup >> backups/backup.log 2>&1
```

**Copy backups and the secrets directory off the host** (to another disk, a NAS or encrypted cloud storage). A backup on the same disk is not a backup.

**Restore** (into the same or a fresh host):
1. Install as in the quick start, but **restore your old `secrets/` directory first**, so `atlas-init` doesn't generate new secrets.
2. Restore the database and IdP from a backup set:

   ```bash
   docker compose run --rm atlas-api atlas-admin restore --from backups/<timestamp>
   ```

3. Start the stack:

   ```bash
   docker compose up -d
   ```

**Test a restore** at least once, on a scratch host or with a different `ATLAS_PGDATA_VOLUME` / `ATLAS_IDP_VOLUME` name.

## Upgrading

1. Read the release notes for breaking changes.
2. Take a backup:

   ```bash
   docker compose run --rm atlas-backup
   ```

3. Update the checkout or bump `ATLAS_IMAGE_TAG` in `.env`, then pull:

   ```bash
   git pull && docker compose pull
   ```

4. Start the new version:

   ```bash
   docker compose up -d
   ```

`atlas-migrate` takes its own pre-migration dump, applies the migrations, and only then lets `atlas-api` start. If a migration fails, the API stays down and the log says why. Roll back by restoring the pre-migration dump and setting `ATLAS_IMAGE_TAG` back to the previous version. Migrations are forward-only.

Again: stop with `docker compose down`, **never** `docker compose down -v`.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| `atlas-api` exits with `SECRET_KEY …` | Weak, placeholder or missing key. Delete the bad line from `secrets/atlas/app.env` and re-run `docker compose up -d` to regenerate it, or set your own value |
| `atlas-api` exits mentioning `example.com` or `https` | You haven't set real HTTPS URLs in `.env` |
| `external volume "atlas_pgdata" not found` | Run `./install.sh`, or `docker volume create atlas_pgdata` (and `atlas_idp`) |
| Login loops or "invalid issuer" | `ATLAS_IDP_PUBLIC_URL` / `ATLAS_OIDC_ISSUER` doesn't exactly match the URL users reach, or the front proxy isn't forwarding `Host` |
| Passkey enrolment fails | The IdP isn't on HTTPS with a trusted certificate, or its hostname changed since enrolment |
| Immich mobile can't log in | Check the mobile redirect override, that the IdP hostname is reachable from outside, and that no Cloudflare Access policy covers the IdP or Immich |
| Every request appears to come from one IP | `ATLAS_REAL_IP_HEADER` / `ATLAS_TRUSTED_PROXY_CIDRS` don't match your front proxy |
| Locked out of the IdP entirely | Run `docker compose exec atlas-api atlas-admin break-glass --user <owner>` on the host, which gives a one-time 10-minute owner login |
