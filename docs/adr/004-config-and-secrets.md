# ADR-004: Config and secrets: fail closed, secrets only from an env file, nothing secret in compose or the repo

- **Status:** Proposed
- **Date:** 2026-10-29
- **Related:** [AUDIT](../AUDIT.md) §3.1 A1, §3.5, §4, §2.3 (coupling 7)

## Context

The audit found:

- `SECRET_KEY` silently defaults to a public constant, and tokens forged with it are accepted (A1, verified).
- `docker-compose.yml` commits a literal `SECRET_KEY` and the MinIO root credentials.
- Config is read by `os.getenv` in four modules at import time, so tests can't isolate the DB.
- `STORAGE_BACKEND` vs `ATLAS_STORAGE_BACKEND` don't match.
- `.env` is missing from the root `.gitignore` and from `.dockerignore`.

The history scan found no real secrets. The placeholders, however, are **functionally** secrets on any deployment that uses them.

**Deploy contract:** secrets come from the env file `/srv/appdata/secrets/app.env`. The repo is public.

## Decision

### 1. One typed `Settings` object, built once and injected

- `atlas.kernel.config.Settings` is a `pydantic-settings` model built in `create_app(settings)`.
- It's passed through FastAPI dependencies and the kernel container. Modules get their own validated sub-settings ([ARCHITECTURE](../ARCHITECTURE.md) §6).
- **No module calls `os.getenv`.** A lint rule (ruff banned-api) forbids `os.getenv`/`os.environ` outside `atlas/kernel/config.py`.
- Tests build `Settings(...)` directly, so there's no global engine and no stray `./atlas.db` (fixes the audit's test-isolation leak).
- Every variable is prefixed `ATLAS_` except the conventional `DATABASE_URL`, `SECRET_KEY` and `TZ`. One name per setting.
- Secret fields are typed `SecretStr`. They are never logged, never included in `repr`, error messages or `/health/ready`, and never returned by any API.

### 2. Fail closed at startup

The process exits non-zero **before binding a socket** if any check fails. The error names the variable but never prints its value.

| Check | Rule |
|---|---|
| `SECRET_KEY` present | Required. No default exists anywhere in code |
| `SECRET_KEY` strong | ≥ 32 bytes of entropy: at least 43 base64url chars or 64 hex chars, generated by `openssl rand -base64 32` or `python -c "import secrets;print(secrets.token_urlsafe(32))"`. Rejects keys under 43 chars and keys with fewer than 16 distinct characters |
| `SECRET_KEY` not a known placeholder | Denylist containing every placeholder ever committed (`dev-secret-change-in-production`, `change-this-in-production`), plus `changeme`, `secret`, `password`, and anything containing `change` + `production` |
| `DATABASE_URL` | Required, must be `postgresql+psycopg://…` in production, and must not contain the denylisted password `atlas` |
| OIDC client settings | Issuer URL must be `https://` in production. Client secret is required and not denylisted |
| `ATLAS_ENV` | `production` (default) or `development`/`test`. **Production is the default.** Forgetting the variable yields the strict mode, never the lax one |
| Production-only rules | Docs disabled, CORS off, cookies `Secure`, HTTPS-only issuer, `ATLAS_PUBLIC_URL` required |
| Connector secrets | Each enabled connector's `secret_ref`s must resolve to a non-empty env var. If not, that **connector** is marked `misconfigured` (the app still starts and the console shows it) |

- There is no auto-generated fallback key in any mode. Development uses a real random key in an untracked `.env.dev` (created by `make dev-secrets`).
- The `test` mode is only for `Settings` constructed in tests, which pass explicit values.

### 3. Where secrets live

| Secret | Location | Consumer |
|---|---|---|
| `SECRET_KEY` (session/CSRF signing, step-up state, key derivation) | `/srv/appdata/secrets/app.env` | atlas-api, atlas-migrate |
| `DATABASE_URL` (includes the app DB password) | same `app.env` | atlas-api, atlas-migrate |
| `ATLAS_OIDC_CLIENT_SECRET` | same `app.env` | atlas-api |
| `ATLAS_IDP_ADMIN_TOKEN` (service account for the console's `IdentityAdmin`) | same `app.env` | atlas-api |
| Connector secrets (e.g. `ATLAS_CONNECTOR_IMMICH_API_KEY`) | same `app.env`, referenced by name | atlas-api |
| Postgres superuser password (`POSTGRES_PASSWORD`) | a **separate** env file in the same secrets directory, read only by the `postgres` service | postgres |
| IdP's own secrets / TLS key | its own env file and volume in the same secrets directory | idp |

**Rules:**
- **The repo and compose contain no secret values.**
  - Compose references files with `env_file:` and contains no `environment:` entries for secrets.
  - Non-secret settings (e.g. `TZ=Asia/Bangkok`, `ATLAS_ENV=production`) may appear in compose.
  - Hostnames are **not** in compose either. They're set in a non-secret, untracked `site.env`, so the public repo carries no homelab details.
- **Least privilege per container.** Postgres doesn't receive the Atlas `SECRET_KEY`, and the API doesn't receive the Postgres superuser password. The app connects as a non-superuser role that owns only the Atlas schemas ([ADR-005](005-database-and-migrations.md)).
- **File permissions.** The secrets directory is `0700` and env files are `0600`, owned by root.
  - Compose reads `env_file` on the host at `up` time, so containers never mount the directory.
  - Creating and rotating the file is a host or Terraform/runbook step. The admin console never edits secrets.
- **Connector secrets are not stored in the DB in v1.**
  - The console stores only non-secret connector config (base URL, enabled flag) plus `secret_ref` names, and shows each ref as "set" or "missing".
  - If we later need console-entered secrets, they'll be encrypted at rest with a key derived from `SECRET_KEY` via HKDF with a purpose label, under a new ADR.

### 4. Repo hygiene (prevents re-leaks)

- Root `.gitignore`: `.env`, `.env.*`, `!.env.example`, `*.env`, `!*.env.example`, `site.env`, `secrets/`.
- `.dockerignore`: the same patterns, plus `.git`, `frontend/node_modules`, `tests/`, `docs/`.
- A committed `deploy/app.env.example` lists **names only**, with comments on how to generate each value.
- **gitleaks** runs in CI on every push and on the full history weekly, and as an optional pre-commit hook. CI fails on any finding.
- `docker-compose.yml` is linted in CI. A small script fails if any `environment:` key matches `(?i)(secret|password|token|key)`.

### 5. Rotation

| Secret | Effect of rotation | Procedure |
|---|---|---|
| `SECRET_KEY` | All sessions and CSRF tokens become invalid, so everyone logs in again | Edit `app.env`, then `docker compose up -d atlas-api`. Optional `SECRET_KEY_PREVIOUS` accepted for verification only during a one-day window |
| DB password | — | `ALTER ROLE`, edit `app.env`, restart api and migrate |
| OIDC client secret | — | Rotate in the IdP, edit `app.env`, restart api |
| IdP admin token | — | Rotate in the IdP, edit `app.env`, restart api |

**Historic placeholders:** if any deployment ever ran with one of the placeholder `SECRET_KEY`s, those are treated as compromised. The fail-closed denylist makes them unusable from now on.

## Consequences

- The first deploy needs a one-time manual step: create the env files from the example. The runbook documents it.
- Misconfiguration becomes loud and immediate (the container exits with a clear message) instead of silently insecure.
- Tests and dev never touch production paths or globals.

## Verification

- Unit tests for `Settings`:
  - missing, short, low-variety or denylisted `SECRET_KEY` each give a startup failure;
  - the error message doesn't contain the value;
  - production is the default mode;
  - production rules are enforced.
- A test asserts that no `os.getenv` appears outside `config.py` (ruff rule).
- CI jobs: gitleaks passes; the compose-secret linter passes; `docker compose config` renders with the example env files.
- A container smoke test: start with a placeholder `SECRET_KEY` and assert exit code ≠ 0 and that `/health` is unreachable.
